# MVC 패턴의 기본 개념

**MVC**는 Model, View, Controller의 약자로, 소프트웨어를 세 가지 핵심 구성 요소로 나누는 디자인 패턴입니다. 사용자 인터페이스를 가진 애플리케이션 개발에 주로 사용되며, 각 구성 요소가 독립적으로 기능하도록 설계하여 코드의 유지보수성과 확장성을 높이는 것이 목표입니다.

## Model

데이터와 비즈니스 로직을 관리합니다. 사용자가 어떤 정보를 요청하거나 수정하든, 그 데이터를 처리하고 저장하는 역할을 합니다. View와 Controller에 대해 알지 못하며, 오직 데이터 그 자체에 집중합니다.

## View

사용자에게 보여지는 화면을 담당합니다. Model이 가진 데이터를 시각적으로 표현하는 역할만 합니다. 사용자의 입력(버튼 클릭, 텍스트 입력 등)은 받지만, 직접 처리하지 않고 Controller에게 전달합니다.

## Controller

Model과 View 사이의 중개자 역할을 합니다. 사용자의 입력(이벤트)을 받아 Model의 데이터를 업데이트하거나, Model에서 변경된 데이터를 View에 반영하도록 지시합니다. 사용자의 요청에 따라 Model을 조작하고, 그 결과에 따라 적절한 View를 선택하여 사용자에게 보여줍니다.

---

## MVC 패턴의 작동 흐름

사용자 입력: 사용자가 View를 통해 무언가를 입력(예: 회원가입 버튼 클릭)합니다.

Controller로 전달: View는 이 입력을 직접 처리하지 않고, Controller에게 전달합니다.

Model 조작: Controller는 사용자의 입력에 따라 Model을 조작합니다. (예: 회원 정보를 Model에 추가)

View 업데이트: Model의 데이터가 변경되면, Controller는 변경된 내용을 반영하여 View를 업데이트하라고 지시합니다. 이 때 View는 Model에서 최신 데이터를 가져와 화면을 다시 그립니다.

이러한 분리 덕분에, Model의 데이터 구조를 바꾸더라도 View나 Controller의 코드를 크게 수정할 필요가 없고, View의 디자인을 변경하더라도 다른 구성 요소에 영향을 주지 않습니다.

## MVC의 장점과 한계

### 장점

유지보수 용이성: 각 구성 요소가 독립적이어서 특정 부분을 수정하거나 개선하기 쉽습니다.

재사용성: Model은 여러 View에서 재사용될 수 있어 코드 중복을 줄일 수 있습니다.

확장성: 새로운 기능을 추가할 때 기존 코드에 영향을 덜 미치면서 확장이 가능합니다.

### 한계

복잡성: 간단한 애플리케이션의 경우, 세 가지 구성 요소를 모두 분리하는 것이 오히려 불필요하게 복잡할 수 있습니다.

Controller의 비대화: 애플리케이션이 커질수록 Controller가 모든 비즈니스 로직을 처리하게 되어 코드가 복잡해지는 'Massive Controller' 문제가 발생할 수 있습니다. 이는 MVC의 본래 의도와 다르게 Controller의 역할이 너무 커지는 현상을 의미합니다.
